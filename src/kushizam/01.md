# MCPで、開発ルールと指摘を共有する

## 課題と従来の運用

AIに設計や実装を頼む中で、自分が想定している開発方針と違うと感じた部分をフィードバック（以下、FB）していました。その内容を次の作業でも使えるように、作業の進め方や判断基準をCodexのSkillとしてまとめてもらってきました。

Skillは設計、実装、レビュー、検証などの場面ごとに分けて、1つのローカルプロジェクトで管理していました。作業後にFBをした上で「今回の開発方針や指摘をSkillへ反映して」と頼み、既存の内容を確認して調整してもらう形です。

Skillに今後の方針を残しても、元の作業でAIが何を行い、どこを指摘し、なぜ直したかったかまでは十分に残していませんでした。別のAIで作業するとき、過去の指摘と理由を参照したい場面と、今後の判断基準として開発方針を変えたい場面があります。

そこで、これまでのSkill運用を起点に、2つの使い方を分けて検証しました。1つは、作業後のFBと理由を記録し、別のAIの実装に引き継ぐこと。もう1つは、今後も使う開発方針をSkill本文に反映し、別のAIから更新後の本文を取得することです。

## MCPの役割

Skill本文の取得・更新と、FBの保存・検索を複数のAIツールから共通の操作で扱うために、MCPを試しました。

**MCP（Model Context Protocol）**は、機能を提供するサーバーと、それを利用するクライアントの間で、機能の情報や引数、結果をやり取りする取り決めです。サーバーの処理を呼び出す機能を **Tool** と呼びます。MCPはCodexやClaude Codeなど、MCPに対応したAIツールで利用できます。

AIツールはToolの名前・説明・引数の形式を取得します。モデルがToolと引数を選ぶと、AIツールがサーバーへ実行を依頼し、応答を会話へ戻します。今回の役割分担は次のとおりです。

<div class="break-inside-avoid">

```text
利用者の依頼・FB → Codex / Claude Code ←→ AIモデル
                         ↕ Toolの呼び出し・応答
                  ローカルのMCPサーバー
                         ↕ 読み取り・更新・保存・検索
                  開発方針・手順の文書 / 記録のDB
```

</div>

MCPを使う場合、AIが会話から選んだ記録内容をToolへ渡し、サーバーが保存します。Toolの処理は自分で実装するため、文書操作に加えてFBの保存・検索などの機能を用意できます。同じ処理は共通スクリプトやCLIでも作れますが、MCPならToolの情報取得・呼び出し・応答を各AIツールの接続機能で扱えます。

## 検証計画

検証は、次の順に進めます。

1. MCPサーバーでの文書取得・保存・再取得
   - 確認すること：用意した文書を取得でき、保存した対応・FB・理由を別の接続から再取得できるか。
   - 期待するメリット：会話を閉じても記録を残し、必要なときに取り出せる。
2. 両AIからの開発方針の取得・更新
   - 確認すること：Skill本文を更新し、相手のAIから同じ本文・バージョンを取得できるか。
   - 期待するメリット：AIツールを替えても、同じ保存先の開発方針を同じ操作で扱える。
3. FB共有方式の比較
   - 確認すること：MCPを使うと、ファイルを直接読み書きする場合より少ない依頼で正しく記録できるか。また、記録した対応・FB・理由を別AIの実装でも利用できるか。
   - 期待するメリット：依頼回数が減れば記録の負担を抑えられ、記録を利用できればFBや理由を説明し直す手間を減らせる。

作業時間や体感的な負担、保守の手間、一般的な実装品質・成功率、理由を添えること単独の効果、自動的な記録、共通スクリプトとの優劣は、今回は検証対象外とします。

検証環境はmacOS、Python 3.14.6、MCP Python SDK `mcp==2.3.0` です。AIツールはCodex CLI 0.167.0-alpha.3.2（GPT-6.1-sol）とClaude Code 2.1.317（Opus 5.5）を使いました。

## 検証1：文書の取得・更新とFBの保存

### 文書を読むTool

文書を読む処理をToolとして公開するため、公式MCP Python SDKの `MCPServer` を使いました。

作業手順を書いた `rules.md` を `server.py` と同じ場所に置きました。以下は、文書を読む部分を単独で動く形にしたコードです。

<div class="break-inside-avoid">

<!-- listing: reading-server -->
```python
from hashlib import sha256
from pathlib import Path
from mcp.server import MCPServer

server = MCPServer("work-notes")
ROOT = Path(__file__).resolve().parent

@server.tool()
def read_policy() -> dict[str, str]:
    """Read the rule document and its content revision."""
    raw = (ROOT / "rules.md").read_bytes()
    return {"body": raw.decode("utf-8"),
            "revision": sha256(raw).hexdigest()}

if __name__ == "__main__":
    server.run(transport="stdio")
```

</div>

`@server.tool()` で `read_policy` をToolとして公開します。このToolは文書の本文と、照合に使うバージョン（本文のSHA-256）を返します。

接続には、標準入出力で通信する `stdio` を使いました。AIツールにPythonの実行ファイルと `server.py` の絶対パスを登録すると、サーバーが子プロセスとして起動します。取得した本文はToolの応答として会話に渡ります。


Pythonクライアントから `read_policy` を呼び出すと、用意した文書の本文が返りました。

### 保存処理の追加

次に、別のAIへ指摘と理由を渡すため、記録の保存・検索用のToolを加えました。保存用の `record_feedback` は記録をSQLiteに書き込み、検索用の `search_feedback` は話題名で記録を取り出します。記録には作業、AIの対応、利用者のFBと理由、話題名、発生IDを含めます。保存・検索のコードは掲載を省きます。

動作確認としてPythonクライアントから、並べ替え関数について「元のリストを並べ替えて返す形に修正した」という対応を保存しました。FBは「元のリストを並べ替えてほしい」、理由は「呼び出し元の同じリストに結果を反映したい」という内容です（要約）。作業内容・話題名も添えて保存し、接続を閉じてから別のサーバープロセスで検索しました。

保存と再取得で返された内容は、次のとおりです。

<div class="break-inside-avoid">

| 入力・操作 | 応答と確認結果 |
| --- | --- |
| 対応・FB・理由を含む記録を保存 | 保存成功の応答と、保存した記録が返った |
| 保存側を閉じ、別プロセスから同じ話題名で検索 | 保存した記録と全項目が一致 |

</div>

### Skill本文への反映

FBの記録には過去の対応や理由を残し、Skill本文には今後の開発方針を反映します。ここでは、文書取得と保存の確認に使ったものとは別のローカルMCPサーバーを使いました。このサーバーは、指定した文書を読む `read_document` のほか、本文の更新、記録の保存・検索のToolを備えています。AIは `propose_change` で変更案を保存し、案を確認してから `apply_proposal` を呼びます。

両AIツールでSkillを更新対象の文書として扱い、取得・変更案の作成・適用をMCP経由で行いました。適用時にはAIツール側で更新Toolの実行を許可しました。

更新対象は、作業手順 `rules.md` とは別に用意した、並べ替え用Skillの `SKILL.md` です。初期本文は「元のリストは変更せず、新しいリストを返す」としました。保存・再取得の確認で使ったFBと理由に、修正前の対応として「新しいリストを返す実装を提示した」と添え、まず記録だけを依頼しました。次に、並べ替えの方針としてSkillへの反映を頼み、相手のAIの新しい会話から取得しました。

<div class="break-inside-avoid">

| 操作 | 両AIで確認した結果 |
| --- | --- |
| FBの記録 | 記録が残り、Skill本文とバージョンは変わらない |
| Skillへの反映 | 元のリスト自体を並べ替えて返す方針と理由に更新。バージョンも変更 |
| 相手のAIで取得 | 更新側と本文・バージョンが一致。元のFB・理由も別に取得できた |

</div>

## 検証2：FB共有の方式比較

この比較では、手順や関連資料をまとめられる **Agent Skills** の形式で、FBの記録・取得の手順を `SKILL.md` に書きました。記録・再取得を頼む際にファイルの場所を明示し、CodexとClaude Codeに読み込ませました。

手順を伝えるSkillと、AIの対応・FB・理由の保存先を分け、次の2方式を用意しました。

<div class="break-inside-avoid">

| 方式 | 記録の保存・取得方法 |
| --- | --- |
| Skill方式（MCPなし） | 作業記録ファイル（JSON形式）をAIが直接読み書きする |
| Skill＋MCP方式 | AIがToolを呼び、サーバーがDBに保存・検索する |

</div>

### 比較条件と初回の実装

整数リストを並べ替える架空の作業で、Skill方式（MCPなし）とSkill＋MCP方式を両方向各1回試し、次の2項目を比較しました。

- 記録の依頼回数：正しい内容の保存・読み直しまでに、利用者が記録を頼んだ回数。
- 別AIでの利用結果：実装の動作と判断理由に、保存したFBの内容が反映されたか。

Skill＋MCP方式では、既存のローカルMCPサーバーの `read_document` で、並べ替えの方針を含まない作業手順を読みます。更新済みのSkillや以前の記録は使わず、この比較で生じるFBを使います。

両方式のSkillには「作業前に文書と関連記録を読み、依頼されたら対応・FB・理由を保存して読み直す」という手順を書きました。依頼内容と保存項目をそろえ、FBの記録と共有を比較しました。Skill本文の改訂は対象外です。

初回は整数リストを小さい順に並べ替えて返す関数 `sort_numbers(values)` と、使い方・判断理由を作るよう依頼しました。この題材の作業手順や記録は読み込ませず、元のリストを変更するかどうかはAIに任せました。表1はその2通りの実装方針です。

<div class="break-inside-avoid">

**表1　並べ替え方による動作の違い**

| 実装方針 | 関数の処理 | 元のリスト | 戻り値 |
| --- | --- | --- | --- |
| A：保持 | `return sorted(values)` | 変えない | 並べ替えた新しいリスト |
| B：変更 | `values.sort()`<br>`return values` | リスト自体を並べ替える | 渡されたものと同じリスト |

</div>

初回に生成された4実装は、すべてAでした。記録を読む前から求める動作だった場合と区別できるよう、その動作とは反対のBを求めるFBを渡しました。

### 記録の依頼回数と別AIでの取得

同じ会話に、次のFBと理由を渡しました。

<div class="break-inside-avoid">

> 渡したリスト自体を小さい順に並べ替え、そのリストを返してください。
>
> 呼び出し元が保持している同じリストに、並べ替えた結果を反映したいからです。

</div>

あわせて、関数と判断理由を修正した上で、指定したSkillに従って今回の対応・FB・理由を記録し、読み直すよう頼みました。修正前後の対応は分け、FBと理由は原文のまま保存するよう伝えています。

両AIとも実装をBへ直し、次の操作で記録を保存して読み直しました。

- Skill方式（MCPなし）：作業記録ファイルへ保存し、読み直した。
- Skill＋MCP方式：`read_document` で同じ本文・バージョンの手順を取得後、`record_feedback` で保存し、検索で確認した。

両方式で対応・FB・理由を保存でき、対応の要約は修正前後のコードと一致しました。FBと理由は原文のまま残りました。比較条件をそろえた試行では、記録依頼はどちらも1度で、MCPによる削減は確認できませんでした。

続いて、相手のAIツールで新しい会話を開き、次の順に作業させました。

<div class="break-inside-avoid">

1. Skillに従い、作業手順の文書と指定した話題の記録を取得する。
2. 初回と同じ依頼で関数を実装する。
3. 記録のどのFBと理由を反映したか、判断理由の文書に残す。

</div>

元の会話やコードファイルは渡さず、新しい依頼文にもFBや理由は書いていません。記録には具体的な修正方法も含まれます。Skill＋MCP方式でCodexが保存し、Claude Codeが取得した「AIの対応」の抜粋です。

<div class="break-inside-avoid">

> 修正前は sorted(values) で新しいリストを返していた。今回は values.sort() で渡されたリスト自体を昇順に並べ替え、return values で同じリストを返すようにした。

</div>

Skill＋MCP方式は `search_feedback` の応答、Skill方式（MCPなし）は作業記録ファイルの読み取り履歴を調べ、相手のAIが保存内容を取得したことを確認しました。

### 結果：動作と理由の変化

別AIが新しい会話で作った関数も、すべてBになりました。結果を表2に示します。矢印は記録するAIから読むAIへの方向です。「初回」「FB後」は保存側の同じ会話、「別AI」は受取側の新しい会話での新規実装を表します。

<div class="break-inside-avoid">

**表2　初回・FB後・記録を読んだ別AIの実装**

| 記録方式 | 共有方向 | 初回 | FB後 | 別AI |
| --- | --- | --- | --- | --- |
| Skill＋MCP方式 | Codex → Claude Code | A | B | B |
| Skill＋MCP方式 | Claude Code → Codex | A | B | B |
| Skill方式（MCPなし） | Codex → Claude Code | A | B | B |

受取側の記録なしの結果は、表2の同じ記録方式で矢印が逆向きの行の「初回」にあたり、いずれもAでした。

生成コードをPythonで実行すると、`[3, 1, 2]` の戻り値はAもBも `[1, 2, 3]` でした。元のリストはAでは `[3, 1, 2]` のまま、Bでは `[1, 2, 3]` に変わりました。

順序の異なる3要素・重複・負数・空リスト・1要素の5入力で、初回・FB後・別AIの計12実装を実行し、表2の分類どおりの動作を確認しました。

別AIの判断理由にも、4件すべてに「呼び出し元が保持する同じリストに結果を反映する」という目的が含まれていました。

## 結果と結論

検証計画に沿って、結果と判断をまとめます。

<div class="break-inside-avoid">

| 計画の確認項目 | 結果と判断 |
| --- | --- |
| 1：取得・保存・再取得 | 文書を取得でき、保存側の接続を閉じた後も、別プロセスから同じ記録を再取得できた |
| 2：開発方針の取得・更新 | 両AIがMCP経由でSkill本文を更新し、相手のAIも更新側と同じ本文・バージョンを取得できた |
| 3：記録の依頼回数 | 両方式とも1度で保存・読み直しができた。MCPによる依頼回数の削減は確認できなかった |
| 3：別AIでの利用結果 | 話題を指定して記録を取得させると、両方式とも実装の動作と判断理由にFBの内容が反映された |

</div>

今回の関数で元のリストを並べ替える理由を別のAIへ伝えるには、対応・FB・理由を記録として残します。検証では作業記録ファイルとMCPのどちらでも、記録を読んだ別のAIの実装と判断理由にFBが反映されました。

同じ並べ替え方を今後の判断基準にすると決めたら、どの作業に適用するかを決めてSkill本文にも反映します。FBの記録後も本文とバージョンは元のままで、更新Toolで反映した後は、相手のAIも更新側と同じ本文とバージョンを取得できました。記録の保存・検索とSkill本文の取得・更新をサーバーにまとめ、両AIから共通のToolで扱いたい場合に、MCPを選べます。

Toolへ独自の処理を加えられる点は、今後の応用にも使えそうです。たとえばFBを集計する処理を追加すれば、自分がどのような点を気にしているかを振り返る仕組みにも広げられそうだと感じました。
