# MCPで、開発ルールと指摘を共有する

## 課題と従来の運用

元々、AIに設計や実装を頼む中で、自分の開発方針と違うと感じた部分をフィードバック（以下、FB）していました。その内容を次の作業でも使えるように、作業の進め方や判断基準をSkillとしてまとめてもらってきました。

**Agent Skills**は、`SKILL.md` を中心に手順や関連資料、必要に応じてスクリプトをまとめ、対応するAIツールで使うための形式です。Skillは設計、実装、レビュー、検証などの場面ごとに分けて、一つのローカルプロジェクトで管理していました。作業後にFBをした上で「今回の方針や指摘をSkillへ反映して」と頼み、既存の内容を確認して調整してもらう形です。

たとえば、処理を共通化することで、かえって複雑になる場合がありました。そこで、「同じ意味で一緒に変わる処理は共有し、独立して変わる処理は、共通化で複雑になるなら個別に残す」という条件をまとめました。ただ、指摘を短いルールにすると、元の対応や、なぜ直したかったのかという理由は省かれます。Skillにまとめたルールとは別に、そのときの対応と理由も記録し、別のAIでも利用できるようにしたいと思いました。

## MCPの役割と検証計画

**MCP（Model Context Protocol）**は、機能を提供するサーバーと、それを利用するクライアントの間で、機能の情報や引数、結果をやり取りする取り決めです。サーバーの処理を呼び出す機能を **Tool** と呼びます。AI間の試験でのクライアントは、CodexとClaude Codeに備わるMCP接続機能です。

AIツールはToolの名前・説明・引数の形式を取得します。モデルがToolと引数を選ぶと、AIツールがサーバーへ実行を依頼し、応答を会話へ戻します。今回の役割分担は次のとおりです。

<div class="break-inside-avoid">

```text
利用者の依頼・FB → Codex / Claude Code ←→ AIモデル
                         ↕ Toolの呼び出し・応答
                  ローカルのMCPサーバー
                         ↕ 読み取り・保存・検索
                  開発ルールの文書 / 記録のDB
```

</div>

Skillは、いつ何を読む・記録するかという手順を伝えます。MCPサーバーには会話全体が自動で渡るわけではなく、利用側のAIが選んだ内容をToolの引数として送ります。入力検査や保存はサーバーに実装します。

同じ処理は、Skillから呼ぶ共通スクリプトやCLIでも作れます。MCPを使う違いは、その処理を、Toolの情報取得・呼び出し・応答を扱う各AIツールの接続機能へ載せられることです。

この構成で、以下の三点を確認しました。

1. 対応・指摘・理由を記録すれば、別AIの実装でも利用できるか。
   - 期待するメリット：AIツールを替える際に、指摘や理由を説明し直す手間を減らせる。
2. MCPを使うと、Skillと共有ファイルの場合より、記録が正しく残るまでの依頼回数が減るか。
   - 期待するメリット：普段のFBを記録する負担を抑えられる。
3. 入力検査や再送への対応を、共通の保存処理に任せられるか。
   - 期待するメリット：どのAIツールからも同じ検査を通し、不十分な入力や重複保存を防ぐ処理を一か所で管理できる。

まずは小さなMCPサーバーを作り、Pythonクライアントで取得・保存・再取得を確認しました。その上で、別の既存サーバーを使って、CodexとClaude Codeでの引き継ぎを比較しました。入力検査・再送処理の動作確認は試作サーバーを対象とし、AI間では正常な記録の保存・引き継ぎを確かめました。

比較は、整数リストの並べ替えという架空の作業について、両方式・両方向を各一回行ったものです。一般的な実装品質・成功率、理由を添えること単独の効果、自動的な記録、共通スクリプトとの優劣を測る試験ではありません。

## 検証1：文書の取得と指摘の保存

### 文書を読むTool

サーバーには、公式MCP Python SDK `mcp==2.3.0` の `MCPServer` を使いました。確認環境はmacOS、Python 3.14.6、入力検査に使うPydanticは2.14.2です。

まず、作業手順を書いた `rules.md` を、サーバーの `server.py` と同じ場所に置きました。文書には「作業の依頼と、その話題に対応する利用者の記録を確認する」と書き、個別の実装方針は指定していません。以下は、試作の文書を読む部分を単独で動く形にしたコードです。

<div class="break-inside-avoid">

<!-- listing: reading-server -->
```python
from hashlib import sha256
from pathlib import Path
from mcp.server import MCPServer

server = MCPServer("work-notes")
ROOT = Path(__file__).resolve().parent

@server.tool()
def read_policy() -> dict[str, str]:
    """Read the rule document and its content revision."""
    raw = (ROOT / "rules.md").read_bytes()
    return {"body": raw.decode("utf-8"),
            "revision": sha256(raw).hexdigest()}

if __name__ == "__main__":
    server.run(transport="stdio")
```

</div>

`work-notes` は、この例に付けた任意のサーバー名です。`@server.tool()` を付けると、SDKが関数名・説明文・型からToolの情報を組み立てます。`read_policy` は「方針を読む」という名前のToolになり、本文を `body`、本文から計算したSHA-256の値を `revision` に返します。この値を文書の版として照合に使い、更新順や基準の正しさは表しません。

`stdio` は標準入力と標準出力を使う通信方式です。AIツールには、Pythonの実行ファイルを起動コマンド、`server.py` の絶対パスを引数として登録します。AIツールがサーバーを子プロセスとして起動するため、公開URLは不要です。返された本文はToolの応答として会話に入り、Skillとして自動登録されるわけではありません。

Pythonクライアントから `read_policy` を呼び、文書を変えずに取得すると本文と版が一致し、一行追記すると両方が変わり、元に戻すと最初の値へ戻ることを確認しました。

### 保存処理の追加

文書を取得できたので、同じ試作サーバーへ、作業後の記録を受け取る `record_feedback` と、話題名で取り出す `search_feedback` を追加しました。保存先はSQLiteです。Skill本文は自動で更新せず、見直す際の判断材料を残します。作業、AIの対応、利用者の指摘、述べられた理由を分け、検索用の話題名と、一度の指摘を識別する発生IDも付けます。

入力の型や空白だけの文字列はPydanticで検査します。利用者が理由を伝えていない場合は `null` とし、推測で補いません。サーバーから利用側へ伝える `instructions` にも、依頼されたときだけ保存すること、理由を推測しないこと、保存結果を読み直すことを書いておきました。

保存Toolには、同じ発生IDで同じ内容が送られたら追加せず、内容が異なれば拒否する処理を実装しました。次はその分岐の抜粋です。`old` はDBから取得した既存の記録、`payload` は今回の入力をJSON文字列にしたものです。接続、照会、新規保存のSQLは省いています。

<div class="break-inside-avoid">

<!-- excerpt: save-retry-branch -->
```python
if old:
    if old[0] != payload:
        raise ToolError(
            "FEEDBACK_CONFLICT: ID already has different data")
    return {"status": "already_recorded",
            "record": json.loads(old[0])}
```

</div>

`ToolError` はSDKのエラーです。発生IDは呼び出し側から渡し、別の作業で同じ指摘が再発した場合は別IDにします。サーバーはそのIDで照会・保存を一つのトランザクション内で行い、重複や衝突を判定します。

Pythonクライアントから、並べ替え関数を「元のリストを並べ替えて返す形に修正した」という対応を保存しました。指摘は「元のリストを並べ替えてほしい」、理由は「呼び出し元の同じリストに結果を反映したい」という内容です（要約）。作業内容・話題名・発生IDも添え、入力を変えて次を確認しました。

<div class="break-inside-avoid">

| 入力・操作 | 応答と確認結果 |
| --- | --- |
| 新しいIDで保存 | `recorded` と保存した記録 |
| 保存側を閉じ、別プロセスから同じ話題名で検索 | 保存した記録と全項目が一致 |
| 同じID・内容を再送 | `already_recorded`（保存済み）。記録は1件のまま |
| 同じIDで指摘だけを変更 | `FEEDBACK_CONFLICT` エラー。元の記録は保持 |
| 新しいIDで理由を省いて保存 | `recorded`。理由は `null` |
| 理由を空白だけにして送信 | 入力エラー。保存されなかった |

</div>

保存処理を確認できたので、次はAI自身に会話から記録する内容を選ばせ、別のAIでも使えるかを調べました。

## 検証2：別AIへの引き継ぎ

### 比較条件と初回の実装

比較には、Codex CLI 0.167.0-alpha.3.2／GPT-6.1-solと、Claude Code 2.1.317／Opus 5.5を使いました。接続先は、1.3の文書取得・保存の試作とは別の既存サーバーです。同じSDK 2.3.0で、文書取得には `read_document`、保存・検索には `record_feedback`・`search_feedback` を使いました。文書の本文は検証1と同じで、並べ替えの方針は含みません。

両AIツールへstdioの起動設定を登録し、Skillには「作業前に文書と関連記録を読み、依頼されたら対応・指摘・理由を保存して読み直す」と記しました。比較相手には、同じ項目を共有JSONファイルへ記録するSkillを用意しました。両方式で依頼内容をそろえ、Skillの場所を明示し、相手が保存した対象の記録を読む条件にしました。

初回は比較用のSkillの読込みを求めず、「整数のリストを小さい順に並べ替える関数 `sort_numbers(values)` を作り、並べ替えたリストを返す。使い方と判断理由も文書に残す」と依頼しました。文書・記録も読み込まず、元のリストを変更するかどうかは指定していません。その選択を、表1の二通りに分けました。

<div class="break-inside-avoid">

**表1　並べ替え方による動作の違い**

| 方針 | 関数の処理 | 元のリスト | 戻り値 |
| --- | --- | --- | --- |
| A：保持 | `return sorted(values)` | 変えない | 並べ替えた新しいリスト |
| B：変更 | `values.sort()`<br>`return values` | リスト自体を並べ替える | 渡されたものと同じリスト |

</div>

両方式の試験で用意した初回の4実装は、すべてAでした。初回からFBで求める方針と同じ実装になっていたら、記録によって変わったかが分かりません。なので、その動作とは反対のBを求めるFBを渡しました。

### FBの記録と別AIでの取得

同じ会話に、次の指摘と理由を渡しました。

<div class="break-inside-avoid">

> 渡したリスト自体を小さい順に並べ替え、そのリストを返してください。
>
> 呼び出し元が保持している同じリストに、並べ替えた結果を反映したいからです。

</div>

あわせて、関数と判断理由を修正した上で、指定したSkillに従って今回の対応・指摘・理由を記録し、読み直すよう頼みました。修正前後の対応は分け、指摘と理由は原文のまま保存するよう伝えています。自分でIDやToolの引数を組み立てる操作は加えていません。

両AIとも実装をBへ直しました。MCP方式では、両AIが `read_document` で同じ本文・版の手順を取得した後に `record_feedback` を呼び、検索で保存内容を確認しました。共有ファイル方式でも、同じ項目を保存して読み直せました。対応の要約は修正前後のコードと一致し、指摘と理由は原文のまま残りました。どちらも一度の記録依頼で進み、追加の依頼回数に差はありませんでした。

続いて、相手のAIツールで新しい会話を開き、実装ファイルのない作業ディレクトリから、次の順に作業させました。

<div class="break-inside-avoid">

1. Skillに従い、開発ルールと指定した話題の記録を取得する。
2. 初回と同じ依頼で関数を実装する。
3. 記録のどの指摘と理由を反映したか、判断理由の文書に残す。

</div>

元の会話やコードファイルは渡さず、新しい依頼文にもFBや理由は書いていません。記録には具体的な修正方法も含まれます。MCP方式でCodexが保存し、Claude Codeが取得した「AIの対応」は、次の文章でした。

<div class="break-inside-avoid">

> 修正前は sorted(values) で新しいリストを返していた。今回は values.sort() で渡されたリスト自体を昇順に並べ替え、return values で同じリストを返すようにした。

</div>

MCP方式は `search_feedback` の応答、共有ファイル方式はJSONファイルの読取り記録を調べ、相手のAIが保存内容を取得したことを確認しました。

### 結果：動作と理由の変化

別AIが新しい会話で作った関数も、すべてBになりました。結果を表2に示します。矢印は記録するAIから読むAIへの方向です。「初回」「FB後」は保存側の同じ会話、「別AI」は受取側の新しい会話での新規実装を表します。

<div class="break-inside-avoid">

**表2　初回・FB後・記録を読んだ別AIの実装**

| 記録方式 | 引き継ぎ方向 | 初回 | FB後 | 別AI |
| --- | --- | --- | --- | --- |
| MCP | Codex → Claude Code | A | B | B |
| MCP | Claude Code → Codex | A | B | B |
| Skill・共有ファイル | Codex → Claude Code | A | B | B |
| Skill・共有ファイル | Claude Code → Codex | A | B | B |

</div>

受取側の記録なしの結果は、表2の同じ記録方式で矢印が逆向きの行の「初回」にあたり、いずれもAでした。

実装の変化は、生成コードをPythonで実行して調べました。たとえば `[3, 1, 2]` を渡すと、戻り値はAもBも `[1, 2, 3]` ですが、呼び出し元のリストはAでは `[3, 1, 2]` のまま、Bでは `[1, 2, 3]` に変わります。Bの戻り値が元のリストと同じオブジェクトであることも、Pythonの `is` で確認しました。

順序の異なる3要素、重複を含むリスト、負数、空リスト、1要素の五つの入力を、初回・FB後・別AIの計12実装へ渡し、いずれも表2のA・Bの分類どおりに動作することを確認しました。

新しい会話で書くよう求めた判断理由も、四件とも、呼び出し元が保持する同じリストに結果を反映するという目的を含んでいました。共有ファイル方式で記録を読んだCodexは理由を自分の言葉に言い換えていましたが、この目的は保たれていました。

## 結果と結論

1.2で置いた三つの問いに対する結果は、次のとおりです。

<div class="break-inside-avoid">

| 問い | 結果と判断 |
| --- | --- |
| 理由付きの記録を別AIでも使えるか | この例では利用できた。記録を読んだ別AIの実装と理由の説明に、FBの内容が反映された |
| MCPで記録依頼を減らせるか | 差は見られなかった。Skillと共有ファイルでも一度の依頼で記録できた |
| 保存処理を共通化できるか | 検証1の試作サーバーで入力検査・再送処理を確認し、AI間の試験では両ツールが共通の保存Toolを呼べた |

</div>

共通の保存処理をToolとして公開したい場合に、MCPを選べます。今回、CodexとClaude Codeから同じTool名・引数の形式で呼べたことが、その構成を確かめる結果になりました。
Toolの内側へ処理を追加すれば、過去会話の取り込みやFBの集計にも広げられます。

今回の検証を通じて、MCPで方針や判断基準を共有し、作業後の指摘を別のAIへ引き継ぐための基本的な動作を確認できました。Toolへ独自の処理を加えられる点は、自分のFBを蓄積し、どのような点を気にしているかを振り返る上でも有効だと感じました。
