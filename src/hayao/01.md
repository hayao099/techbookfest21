# ローカルLLMにおけるCPU推論の最適化技法

## はじめに

近年，アプリケーション開発から日常の情報検索，広告制作，業務効率化に至るまで，LLMの活用事例が急増している．しかし，一般的なLLMの動作にはGPUが必要不可欠である．半導体供給の不安定化や価格高騰により，GPUの入手は容易ではない．本セクションでは，GPU環境を必要とせずに安価にLLMを動作させるための効率的なチューニング手法を紹介する．

## 想定する読者

* Transformer，Tokenizerをはじめとした基本的なLLMの仕組みについて理解している．
* 基本的なLinux コマンドが扱える．

## 前提

* GPUやNPUなどの専用AIアクセラレータは扱わない．
* 対象のCPUアーキテクチャは x86_64 とする．
* 対象モデルはテキスト生成タスクのみとする．

## 事前知識

### CPUローカル推論におけるボトルネック

CPUのみでLLMを動作させる際，サーバに搭載されたメインメモリの帯域幅が最大のボトルネックとなる．これは，メモリ帯域の理論上限を超えるスループットの達成が原理的に不可能であることを意味する．したがって，CPU推論のチューニングにおいては，メモリ帯域を極限まで引き出し，ハードウェアの物理限界に近い処理効率を実現することが主目標となる．

このため，LLMのトークン生成スループットは，メモリのデータ転送レートとチャネル数に強く依存する．

本セクションで検証したサーバに搭載されているDDR4-2400を例に挙げると，データ転送レートは 2,400 MT/s，バス幅は 64 bit（8 bytes）であるため，シングルチャネル構成時のメモリ帯域幅は 19.2 GB/s となる．

```
2400 [MT/s] * 8 [B] = 19.2 [GB/s]

```

本検証環境はクアッドチャネル構成であるため理論最大帯域は 76.8 GB/s となるが，DRAMのリフレッシュオーバーヘッドやコマンドバス競合等による損失（実効効率 約75%〜85%）を考慮すると，約57.6〜65.3 GB/s がチューニングにおける現実的な目標値となる．

```
19.2 [GB/s] * 4 [channels] * 0.75 = 57.6 [GB/s]

```

### トークン生成スループットの算出式

トークン生成（Decode）スループットの理論的な概算は，以下の式で求められる．

```
Throughput [tokens/s] ≈ 実効メモリ帯域幅 [GB/s] / モデルサイズ [GB]

```

ただし，モデルの内部構造（密結合モデルかMoEか）やKVキャッシュの読み出し量によって変動するため，実際の性能は本式の値と完全に一致するわけではない点に留意されたい．

## チューニング項目

### taskset（CPUアフィニティの設定）

LinuxのCPUアフィニティを設定し，プロセスが使用するCPUコアを物理コアに限定してバインドする．
割り当てスレッド数を物理コア数と一致させ，Hyper-Threadingによる論理コア（SMTスレッド）への無秩序なスレッド配置や，コア間の頻繁なコンテキストスイッチを防ぐ．これにより，L1/L2キャッシュのヒット率が安定し，スレッド間のバリア同期待ち遅延が抑制され，推論速度のブレを排除できる．

### --threads / --threads-batch

PrefillおよびDecode処理に割り当てるスレッド数を物理コア数に合わせる．`taskset` と併用することで，Hyper-Threadingに起因する同一物理コア内の演算器（ALU/FPU）競合を回避する．

### --no-mmap

OSのメモリマップ（`mmap`）機能を使用せず，モデルの重みデータを起動時に直接ヒープメモリへ展開する．
推論実行中のページフォールトやファイルシステム経由のI/Oオーバーヘッドを排除し，物理メモリ上に重みを常駐させることで，CPUからのメモリアクセスレイテンシを安定化させる．

### --mlock

`mlock()` システムコールを発行し，確保したモデルのメモリ領域を物理RAM上にロックする．
OSの仮想メモリ管理機構によってモデルの重みデータがスワップ領域へページアウトされるのを防ぎ，突発的なスループット低下（レイテンシスパイク）を抑止する．

### --batch-size

Prefill時に一度に処理するトークン数を設定する．CPUの共有L3キャッシュサイズに収まるよう適切に調整することで，キャッシュミスを減らし，Prefill処理のスループットを向上させる．

### --ubatch-size

物理的な計算の最小単位となるマイクロバッチサイズを設定する．
演算時の作業用一時メモリのサイズを抑制し，CPUキャッシュのヒット率を高める．`--batch-size` と連動させることで，CPU推論に最適化されたパイプライン処理を実現する．

### --graph-reuse

推論ステップごとに計算グラフ（ggml compute graph）を破棄・再構築せず，メモリ上にキャッシュして再利用する．
1トークン出力ごとに発生していたCPU側のグラフ構築オーバーヘッドを排除し，CPU演算が律速になりやすい環境でトークン生成速度を底上げする．

### --flash-attn

FlashAttentionを有効化する．通常のAttention計算で発生する巨大な中間テンソルをメインメモリ上に展開せず，ブロック単位でCPUキャッシュ（L1/L2/L3）内でタイリング計算させる．コンテキスト長が伸長した際のメモリアクセス負荷を低減し，スループットの低下を防ぐ．

### --cpu-moe

Mixture of Experts（MoE）モデルにおけるExpert部分の重み配置および計算ルーチンを，CPU演算向けに最適化する．なお，本オプションはモデルがMoEアーキテクチャを採用している場合にのみ機能する．

### --merge-up-gate-experts

MoEの各Expert内にある「Up-projection」と「Gate-projection」の2つの重みテンソルを行列結合する．
従来2回に分かれていた行列積計算と重み読み出しを1回の結合演算に集約することで，メモリからの重みフェッチ回数を削減し，MoE層の計算スループットを向上させる．

### --merge-qkv

Self-Attention機構における Query（Q），Key（K），Value（V）の各射影重みテンソルを1つのテンソルに統合して計算する．
Q, K, V それぞれの重みを個別にメモリからロードするオーバーヘッドを排除し，1回の結合行列積で処理を完結させることで，メモリバスへのアクセス頻度を低減する．

### Transparent Huge Pages（THP）

LLMの推論処理は数十GBに及ぶ重みやKVキャッシュ領域を毎トークン走査するため，標準の4KBページでは仮想アドレス変換キャッシュ（TLB）の容量を瞬時に枯渇させてしまう．THPを有効化して2MBの巨大ページを適用することで，TLBミス率を大幅に低減させる．

```bash
echo always | sudo tee /sys/kernel/mm/transparent_hugepage/enabled

```

### CPU周波数ガバナーの performance 化

CPU周波数ガバナーを `performance` に固定し，全コアを常時All-Core Turbo周波数で動作させる．Pステートの遷移遅延や，コア間のクロック周波数のばらつきによる同期待ちを排除する．

```bash
sudo cpupower frequency-set -g performance

```

### スワップ発生の抑制（vm.swappiness）

モデル本体やコンテキストによってRAMが圧迫された際，OSが推論プロセスのメモリページをディスクへ退避させるのを抑制する．これにより，I/O待ちによる推論速度の急低下を防ぐ．

```bash
sudo sysctl -w vm.swappiness=1

```

## 考察

チューニングによる性能向上がPrefillで約+1.4%，Decodeで約+4.2%と小幅にとどまったのは，チューニング前の段階でハードウェア（CPUおよびメモリバス）の物理的限界にほぼ達していたと考えられる．

わずかにthroughputが向上していることから設定内容自体は効いているが，マシンのポテンシャルをすでに極限まで使い切っている状態であったといえる．測定結果から読み取れる技術的要因と考察は以下の通りである．

### メモリ帯域が実効飽和点（物理限界）に達している

* Broadwell-EPの実効限界: DDR4-2400 Quad-Channelの理論最大帯域は 76.80 GB/s だが，Broadwell世代のメモリコントローラの実効効率（STREAMベンチマーク等の実測値）は通常 68〜72%（約52〜55 GB/s）が物理的な上限となる．
* 測定値との一致: チューニング前の最大Read帯域が 50.46 GB/s，チューニング後が 52.20 GB/s（使用率69.99%）となっており，ハードウェアの限界値にほぼ張り付いている．
* ソフトウェア側で並列処理やスケジューリングをいくら最適化しても，メモリから重みを吸い上げる物理帯域がボトルネック（メモリバウンド）となっているため，スループットの伸びが頭打ちになっている．

### MoE（Active 3B）の帯域需要とDecode速度の整合性

* Qwen3.6-35B-A3Bは総パラメータ35B，アクティブ約3BのMoEモデルである．Q4_K_M量子化時，1トークン生成ごとに読み出すアクティブ重みはおよそ 1.8〜2.2 GB に達する．
* 計算上の帯域需要:　18.93 [tok/s] * 2.0 [GB] ≈ 37.86 [GB]
* この数値は測定結果の「負荷時 平均使用率: 44.47 GB/s」とほぼ整合する．Decode処理がCPU演算ではなく，完全にメモリ帯域がボトルネックになっていることの裏付けとなる．

### 各チューニング項目の効果と相殺要因

* `taskset -c 0-19` / `--threads 20`
SMT（論理スレッド）の競合を回避し，物理20コアに1:1で割り当てる設計自体は妥当である．ただし演算器の空き待ちではなくメモリ待ちが生じているため，速度向上幅としては微増にとどまった．


* `--flash-attn on`
FlashAttentionはコンテキスト長が数千〜数万トークンに達した際に計算量・メモリ消費量を大きく削減する．今回の測定（Prefill 799トークン / Decode 1024トークン）ではコンテキストが短いため，効果が表面化しにくい．


* `--cache-type-k q8_0` / `--cache-type-v q8_0`
デフォルト（f16）に対してKVキャッシュ転送量を半減させる設定だが，1024トークン程度ではKVキャッシュの総サイズが数十MBにすぎず，GB単位のモデル重み転送量と比較して影響が軽微である．AVX2による量子化・逆量子化のオーバーヘッドと相殺され，速度差が小さくなったと考えられる．


* `transparent_hugepage=always` / `performance` ガバナー / `vm.swappiness=1`
負荷時平均帯域が 42.79 GB/s から 44.47 GB/s へ底上げされ，全体平均使用率も向上していることから，レイテンシのばらつき低減や処理の安定化には確実に寄与している．

### 評価

2016年世代のAVX2 CPU（Xeon E5 v4）において，35BクラスのMoEモデルを 約19 tokens/s で処理できている点は，ik_llama.cppのMoE最適化（`--cpu-moe` 等）を含め，ハードウェアの能力を限界近くまで引き出せている状態と評価できる．
