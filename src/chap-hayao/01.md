# ローカルLLMにおけるCPU推論の最適化技法

## はじめに

近年，アプリケーション開発から日常の情報検索，広告制作，業務効率化に至るまで，LLMの活用事例が急増している．しかし，一般的なLLMの動作にはGPUが必要不可欠である．半導体供給の不安定化や価格高騰により，GPUの入手は容易ではない．本セクションでは，GPU環境を必要とせずに安価にLLMを動作させるための効率的なチューニング手法を紹介する．

## 想定する読者

* Transformer，Tokenizerをはじめとした基本的なLLMの仕組みについて理解している．
* 基本的なLinux コマンドが扱える．

## 前提

* AIアクセラレーター(GPU,NPUなど)は扱わない．
* 利用するCPU Arch は，x86_64とする．
* LLMモデルは，text生成のみとする．

## 事前知識

### CPU Local LLM のボトルネック
CPUのみでLLMを動作させる際，サーバに搭載されたメインメモリの帯域幅がボトルネックとなる．これは，メモリ帯域の理論値を超えるスループットの実現が不可能であることを意味する．したがって，チューニングにおいてはメモリ帯域を最大限に活用し，可能な限り高い処理効率を実現することが目標となる．

このことから，LLMが出力するトークン生成スループットは，メモリのデータ転送レートとチャンネル数に依存する．

本セクションで検証したサーバに搭載されているDDR4-2400を例に挙げると，データ転送レートは，2400 MT/s，バス幅は64bit(8bytes)であるから，シングルチャンネルの場合のメモリ帯域幅は，19.2 GB/s となる．

```
2400 [MT/s] * 8 [B] = 19.2 [GB/s]
```

ここから，本セクションで検証したサーバがクアッドチャネルであることと，DRAMのリフレッシュ損失やコマンドバスの競合等の損失(約75%~85%)を考慮すると，約57.6~65.3 GB/s がチューニングの目標となる．

```
19.2 [GB/s] * 4 [channel] * 0.75 = 57.6 [GB/s]
```

### トークン生成スループット
LLMが出力するトークン生成スループットの概算は，次の式で決まる．

```
Throughput [token/s] ≈ 実行メモリ帯域幅 [GB/s] / モデルサイズ [GB] ・・・①
```

ただし，LLMモデルの構造，KV cache読み出し量によって異なるため，上記の式の限りではないことがあることに注意する．

## チューニング

### taskset
LinuxのCPUアフィニティ（親和性）を設定し，プロセスが使用するCPUコアを物理コアに指定する．
これを論理コア数と同じ数にすることで，hyperthreadingによるスレッド配置やコア間の頻繁なコンテキストスイッチを防ぐ．L1/L2キャッシュのヒット率が安定し、スレッド間の同期待ち（バリア同期遅延）が削減され、推論速度のブレがなくなる．

### --threads / --threads-batch
Prefill，decodeに利用するスレッド数を物理コア数に合わせる．これは，tasksetと同様に，hyperthreadingによる物理コア同士による演算器（ALU/FPU）の奪い合いを防ぐ．

### --no-mmap
OSのメモリマップ（mmap）機能を使わず，モデルの重みを起動時に直接ヒープメモリへ読み込ませる．
これは，推論実行中にOSのページフォールト監視やファイルシステム経由のオーバーヘッドが発生させないことで，物理メモリに直接展開されるため、CPUからのメモリアクセスレイテンシが向上する．

### --mlock
mlock() システムコールを発行し，確保したモデルのメモリ領域を物理RAMに固定する．
これは，OSのメモリ管理機能によってモデルの重みデータがスワップ領域にページアウトされるのを完全に遮断し，突発的なフレームレートの急低下を防ぐ．

### --batch-size
Prefill時のトークン数を，CPUの共有L3キャッシュ以内にし，Prefillの処理スループットを向上させる．

### --ubatch-size
物理的な計算の最小単位となるmicro batch size を設定する．
これは，演算時の作業用一時メモリの消費サイズを抑制し，CPUキャッシュヒット率を限界まで高める．
--batch-size と連動してCPU推論に最適化された小分けのパイプライン処理を実現する．

### --graph-reuse
推論ステップごとに計算グラフ（ggml compute graph）を毎回破棄・再構築せず，メモリ上に残して再利用する．
1トークン出力ごとに発生していたCPU側のグラフ構築オーバーヘッドをゼロにし，CPU演算速度が律速になりやすい環境でトークン生成速度を底上げする．

### --flash-attn
Flash Attentionを有効化する．通常のAttention計算で発生する巨大なAttention行列をメモリ上に展開せず，ブロック単位でCPUのL1/L2/L3キャッシュ内で直接計算させる．コンテキスト長が伸びた際のアテンション計算のメモリ帯域消費を激減させ，スループットの低下を防ぐ．

### --cpu-moe
Mixture of Experts(MoE)モデルのExpert部分の重み配置および計算ルーチンをCPU演算向けに最適化する．ただし，LLMモデルがMoEに対応している必要があることに注意する．

### --merge-up-gate-experts
MoEの各Expert内にある「Up-projection」と「Gate-projection」の2つの重みテンソルを行列結合する．
別々に2回行われていた行列積計算とメモリ読み出しを，1回の結合演算にまとめ，メモリからの重みフェッチ回数が削減され，MoE層の計算スループットが向上する．

### --merge-qkv
Self-Attention機構における Query (Q), Key (K), Value (V) の射影重みテンソルを1つの大きなテンソルに結合して計算する．
Q, K, V それぞれの重みを個別にメモリからロードするオーバーヘッドを排除し，1回の結合行列積で処理を完結させることで，メモリ帯域へのアクセス頻度を減らす．

### Transparent Huge Pages (THP)
LLM推論は数十GBの重み・KVキャッシュ領域を毎トークン走査するため，標準の4KBページの仮想アドレス変換キャッシュ(TLB)の容量を瞬時に使い果たす．このため，THPを有効化して2MBページにすることでTLBミスを低減させる．

```
echo always | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
```

### CPU周波数ガバナーのperformance化
CPU周波数ガバナーをperformance に固定し，搭載コアすべてを常時All-Core Turbo周波数に張り付かせ，スレッド間のクロックばらつきによる同期遅延を排除する．

```
sudo cpupower frequency-set -g performance
```

### swapoff
モデル本体とコンテキストでRAM消費が逼迫した際，OSが推論プロセスのメモリページをディスクに逃がすのを阻止する．推論速度を低下させるのを防ぐ．

```
sudo sysctl -w vm.swappiness=1
```


## 検証環境

* CPU : Intel(R) Xeon(R) CPU E5-2698 v4 @ 2.20GHz　(20 cores/ 40 threads)
* L2 Cache: 20 x 256 KB
* L3 Cache: 50 MB
* Memory : 64 GB DDR4-2400
* OS : Ubuntu24.04
* LLM Model : Qwen3.6-35B-A3B-UD-Q4_K_M.gguf (unsloth)

## 検証方法
本書で紹介したチューニング方法の実施の有無で推論時のメモリ帯域幅の使用率と，トークン生成スループット比較する．
ただし，ik_llama.cppのビルド，モデルのダウンロードは実施済みとする．

* チューニング無
1. 下記のllama-serverを起動するスクリプトを実行する．

```
~/ik_llama.cpp/build/bin/llama-server \
  --model ~/ik_llama.cpp/models/Qwen3.6-35B-A3B-UD-Q4_K_M.gguf \
  --parallel 1 \
  --conversation \
  --color \
  --jinja \
  --host 0.0.0.0 --port 8000
```

2. llama-benchを用いて，推論をさせる．

3. 推論時のメモリ帯域幅の使用率と，トークン生成スループットを計測する．


* チューニング有
1. OS側のチューニングを行う．

```
echo always | sudo tee /sys/kernel/mm/transparent_hugepage/enabled
sudo cpupower frequency-set -g performance
sudo sysctl -w vm.swappiness=1
```

2. 下記のllama-serverを起動するスクリプトを実行する．

```
taskset -c 0-19 ~/ik_llama.cpp/build/bin/llama-server \
  --model ~/ik_llama.cpp/models/Qwen3.6-35B-A3B-UD-Q4_K_M.gguf \
  --parallel 1 \
  --conversation \
  --color \
  --jinja \
  --host 0.0.0.0 --port 8000 \
  --threads 20 \
  --threads-batch 20 \
  --ctx-size 32768 \
  --cache-type-k q8_0 \
  --cache-type-v q8_0 \
  --no-mmap \
  --mlock \
  --batch-size 512 \
  --ubatch-size 256 \
  --graph-reuse \
  --flash-attn on \
  --cpu-moe \
  --merge-up-gate-experts \
  --merge-qkv
```

2. llama-benchを用いて，推論をさせる．

3. 推論時のメモリ帯域幅の使用率と，トークン生成スループットを計測する．

メモリ帯域幅の使用率は，pcm-memoryを用いて計測する．

```
sudo pcm-memory 1 -csv=memory_log.csv
```
